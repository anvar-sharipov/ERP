# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

MyERP is a multi-tenant ERP/accounting platform (1C-like) built with Django + django-tenants (schema-per-company on PostgreSQL) and a React/TypeScript SPA. Core domain: chart of accounts with double-entry bookkeeping, no-code directories (справочники) with JSONB fields, and per-method RBAC with live WebSocket permission/scope updates.

Backend and frontend code comments, commit messages, and much of the domain vocabulary are in Russian — match that when editing existing files.

## Git Policy

- НЕ выполнять никаких git-команд самостоятельно (git add, git commit, git push, git checkout, git reset и т.д.), кроме `git status` и `git diff` для проверки изменений — их можно использовать для информации.
- НЕ пушить и НЕ коммитить ничего в GitHub ни при каких обстоятельствах, даже если задача выглядит завершённой.
- Все коммиты и пуши в GitHub делает только пользователь вручную.
- Если нужно проверить, применились ли миграции или изменения — используй `git status` / `git diff`, но не изменяй состояние репозитория.

## Working conventions

- **Always communicate with the user in Russian**, regardless of what language they type in — chat responses, questions, summaries, everything user-facing. This is independent of the existing rule that code/comments/commit messages match the codebase's Russian convention; this one is specifically about the conversation itself.
- **Token/usage budget is a priority.** Before starting any task that touches 10+ files or requires a full-project sweep (e.g. project-wide i18n audits, renaming/refactoring across the codebase, styling changes applied everywhere), do NOT start executing immediately. First scope the real size (how many files, rough complexity/time), then stop and ask the user to confirm they want to proceed now at that scope, rather than splitting it into smaller batches. Only proceed once they've explicitly confirmed.
- **Save tokens everywhere it doesn't cost quality or reliability:**
  - Don't read a whole file when only one method/function is needed — use targeted search (grep/exact path) instead of pulling in the entire file.
  - Don't dump long logs, stack traces, or verbose command output — surface only the relevant part (the error, the result), drop the rest.
  - Don't repeat unchanged code in a response — show only the diff/changed parts.
  - Don't explain at length what wasn't asked — answer briefly and to the point by default, expand only if asked to.
  - Don't re-ask things already in `CLAUDE.md`, project memory, or already said earlier in this session.
  - Before big operations (full refactor, many files) — propose a short plan for confirmation first, don't generate a huge diff right away.
  - For a small task, don't spread it across several tools/steps if one precise action solves it.
  - None of this may reduce code/test/solution quality — if a correct result genuinely requires reading the whole file or a detailed explanation, do that. This is about cutting noise, not cutting substance.
- **Don't run the backend test suite after every small edit — it burns tokens fast.** Only run tests when: (1) the user explicitly asks, or (2) once, after finishing a whole logical chunk of work (e.g. all the edits for one feature/bugfix), not after each individual file change within it. When you do run tests, scope the run to what the change could plausibly affect (e.g. `python manage.py test accounting.tests.test_bulk_destroy` for a `BulkDestroyMixin` change — not the entire `accounting.tests` package) rather than the full suite by default. When reporting results, don't paste the full verbose log (migration output, passing-test dots, unrelated warnings/stack traces) — give a one-line summary (e.g. "5 passed") and, only for failures, the specific failing test name plus its error text. Passing output and noise should not linger in the conversation or context.
- **When asked to do or change something, if a better approach exists, say so before implementing.** Don't silently execute the literal request if you know a more correct/idiomatic/robust way to do it (matching how professional engineers would approach it) — briefly explain the better option and its tradeoff first, then either proceed with it once confirmed or implement what was asked if the user still prefers that. Don't implement the suboptimal version first and mention the better one afterward.
- **Every new/changed serializer, view, model method, or business-logic side effect in `backend/accounting/` and `backend/users/` must consider all three of — always, not just for brand-new endpoints:**
  1. **RBAC** — wire `get_permissions()` to `users/permissions.py::_rbac(action, resource)` (or `HasPermission(resource, action)`) so the endpoint is actually gated per HTTP method, not left open by omission.
  2. **Scope** — if the model/queryset has a `branch`/`warehouse` (or similar) field, filter it through `users/scoping.py::apply_scope(queryset, user, branch_field=..., warehouse_field=...)` so users only see data within their assigned branches/warehouses.
  3. **Audit log** — if the model is business data worth auditing (documents, transactions, directories, employees, products, etc.), have the ViewSet inherit `accounting/mixins.py::AuditMixin` (see `product_views.py`, `account_views.py`, `directory_views.py`, `employee_views.py`, `transaction_views.py` for existing examples) so create/update/delete get written to `AuditLog`. **`AuditMixin` only hooks `perform_create`/`perform_update`/`perform_destroy` on a standard ModelViewSet — it does NOT catch changes made inside custom `@action` methods (e.g. `Document.post()`/`unpost()`) or via `QuerySet.update()`/bulk operations, since those bypass the serializer save path and Django signals entirely.** Any model method that mutates a business-data field as a side effect (e.g. `Document.post()` updating `Product.cost_price`) must write its own explicit `AuditLog.objects.create(...)` call — don't assume `AuditMixin` on the model's own ViewSet covers side effects on a *different* model, or that it covers a custom action on the *same* model.
  **Every `AuditLog` entry's `changed_data` must be explicit and detailed, never empty/blank and never a raw dumped object** — this is not optional polish, it's the whole point of an audit log (a blank "—" or an unreadable `[object Object]` is equivalent to not logging at all from a "can we reconstruct what happened" standpoint). Concretely:
  - Don't call `_write_log(...)` with no `changed_data` (defaults to `{}`, renders as "—" in `AuditLogPage.tsx`) just because the action doesn't naturally produce a Django-style field diff — write an explicit dict describing what happened instead (see `ClosedPeriodViewSet.perform_create`/`destroy` in `transaction_views.py` for the fixed example: closing/reopening a day used to log with no `changed_data` at all, or a raw `{'snapshot': {...}}` that rendered as `[object Object]` — now both write a plain dict of human-readable key → value pairs).
  - `AuditLogPage.tsx`'s `changed_data` column only renders a nice red→green "before → after" view for values shaped exactly `{before: ..., after: ...}` — anything else (a plain string, a nested object) renders via `String(value)`, so a nested object/dict value will literally show as `[object Object]` on screen. When you want the before/after treatment, shape the value that way explicitly; for anything else, keep it a plain string.
  - For any action with a meaningful "why" (an admin override, a reopen, a manual correction) — capture the reason as an explicit field in `changed_data` (see `ClosedPeriodViewSet.destroy()`'s mandatory `note` — validated non-empty server-side, always included in the log), don't rely on the actor's identity/timestamp alone to imply intent later.
  Don't add a new serializer/view/model-mutation without explicitly deciding on all three — it's easy to silently ship something that's technically working but unprotected, unscoped, or unaudited. This applies to every change, not just ones that look like "adding a new endpoint."
- **After adding any new Django model to `accounting`, `users`, or `chat`, run `python manage.py sync_permissions`.** This command (`users/management/commands/sync_permissions.py`) walks every model in those three apps, per tenant schema, and creates a `Permission(resource=model_name, action=<GET|POST|PUT|PATCH|DELETE>)` row for any that don't exist yet. Until it's run, there's no `Permission` row for the new model at all, so no Role can ever be granted access to it — the RBAC check from the item above will silently deny everyone (including admins assigning roles) regardless of how correctly `get_permissions()` is wired. Run it for all tenants (no args) or a specific one (`--schema <name>`) right after the migration that adds the model.
- **Every Excel export must use `frontend/src/core/utils/excelHelpers.ts::addExcelHeader(workbook, worksheet, company, user, t)`** as its baseline — it sets the standard `pageSetup` (portrait, fit-to-width, margins, horizontal-centered), adds the company logo, and a company/user/date info block. Don't hand-roll a different `pageSetup` per export; if a new export needs different page settings, extend `addExcelHeader` (or a shared variant) rather than diverging per-page.
- **Screen, Ctrl+P print, and Excel export must never drift apart.** When a page's on-screen display changes (a field is added/removed, a column becomes visible/hidden, a total is recalculated differently), the same change must be reflected in that page's print view (`print:` Tailwind classes / print-only blocks) and its Excel export — driven from the same underlying data/column-visibility state, not three independently-maintained copies. See `features/accounting/pages/Documents/Invoice/` for the pattern: `ProductRow`'s `columns`/`visibleScreen`, `Vars.ts`'s shared calc functions (`lineTotal`, `lineGross`, `calcRowIncome`), and `exportDocumentExcel.ts` all consume the same `items`/`columns`/totals rather than recomputing their own version.
  **This also covers view-mode/grouping toggles, not just column visibility.** If a page has a state toggle that changes how rows are organized on screen (grouped vs. flat, grouped by category vs. by brand, filtered to one agent, etc. — e.g. `SubcontoBreakdownPage.tsx`'s `groupByAgent`/agent filter, or `ProductTurnoverPage.tsx`'s `groupBy`), the Excel export must take that same page state as input and reproduce the same structure (same grouping, same subtotals, same filtered subset) — never just dump the full/ungrouped dataset regardless of what's currently configured on screen. Pass the current toggle state and the already-filtered/grouped rows into the export function; don't have the export function re-derive its own default view independent of what the user is actually looking at.
- **When asked to "add Excel" (export to Excel) for a page, the button/UI trigger always goes in the right sidebar** (`core/context/SidebarRightContext.tsx::useSidebar` → `setSidebarContent`), not inline in the page's main content area — this matches where `DocumentFormPage.tsx` puts its Excel button and keeps the pattern consistent across pages.
- **In Excel exports, text must never be clipped/hidden behind a neighboring cell — it must always render in full.** ExcelJS doesn't wrap or auto-widen a cell to fit its content; a text-labeled cell that's merely "the column next to it happens to be empty" only looks fine by luck, and breaks the moment a real value lands in that neighbor (exactly what happened with the header info block and the totals-row labels). The fix, consistently: `worksheet.mergeCells(rowNum, startCol, rowNum, endCol)` across enough columns to hold the text, regardless of whatever width that individual column ends up with elsewhere in the sheet — see `addExcelHeader` (label/value merge) and `exportDocumentExcel.ts::addTotalRow` (label merged + right-aligned so it doesn't run into the value cell) for the established pattern. Don't rely on overflow-into-an-empty-cell as the plan — merge explicitly. Also, when merging a range, always write the cell's value into the range's own anchor (top-left/`startCol`) cell — Excel keeps only the anchor cell's value on merge and silently discards anything written to another cell inside that same range.
- **In Excel exports, monetary/numeric sums (price, discount, total, income) must use a thousand-separated number format**, e.g. `numFmt = "#,##0.00"` (see `exportDocumentExcel.ts::FLOAT_NUMFMT`), so values render as `5 050,00` / `1 000 000,00` rather than plain `5050.00` — matches how real documents display sums, and the separator/decimal character adapts to Excel's own regional settings.
- **Excel exports must look like a plain, serious business document — restrained black/gray, never a colorful "presentation" palette.** Header rows: light gray fill (`#E0E0E0`), bold black text. Subtotal rows: very light gray (`#F2F2F2`). Grand-total rows: a slightly darker gray than subtotals (`#D9D9D9`) purely to distinguish the level, still bold black text — never colored fills (green/indigo/blue) with white text, never a different accent color per section. See `exportDocumentExcel.ts` for the original baseline of this palette, and `exportSubcontoBreakdownExcel.ts`/`exportSubcontoCardExcel.ts::HEADER_FILL/SUBTOTAL_FILL/GRANDTOTAL_FILL` for the exact hex values to reuse — don't invent a new color scheme per report. This applies to every Excel export in the app, not just new ones; if you're already touching an older colorful one, bring it in line, but don't go do an uninvited repo-wide sweep (see the token-budget rule above).
- **Every Excel export whose on-screen table has a "№" row-numbering column must include that same numbering column in the export — no exceptions.** Check the screen table first: if it has a leading "№" column (most report/list tables do — `Table.tsx`, `ProductTurnoverTable.tsx`, `SubcontoBreakdownPage.tsx`, `SubcontoCardPage.tsx`, document line items, etc.), the export must too, in the same position, with the same numbering scheme (continuous across grouped sections if the screen's numbering is continuous — see `exportSubcontoBreakdownExcel.ts`, where the counter is *not* reset per agent group, matching the shared `rowIdx` used on screen). The only legitimate exception is a table whose leftmost column is already a natural identifier instead of a running number (e.g. `OSVTable.tsx`/`exportOSVExcel.ts` — accounts are identified by their `code`, there's no "№" column on screen at all, so none is expected in the export either). **Concrete bug this rule exists because of:** `exportSubcontoBreakdownExcel.ts` and `exportSubcontoCardExcel.ts` both shipped without a "№" column even though their on-screen counterparts (`SubcontoBreakdownPage.tsx`/`SubcontoCardPage.tsx`) both have one — a plain screen/export drift of exactly the kind the "never drift apart" rule above already prohibits, just easy to miss because a missing column doesn't look broken, it just looks like a different (still plausible) design.
- **Every page must have a "?" help button** with a detailed instruction: what the page does, and what each button/element on it does. Build this automatically for every new page — don't wait to be asked, and don't call it out to the user when you do it. No shared help component exists yet as of this writing; establish one (e.g. `components/ui/HelpButton.tsx` or similar) the first time this applies, then reuse it consistently across pages rather than hand-rolling a one-off per page.
- **For every CRUD operation with non-trivial logic (validation, permission/access-rights checks, side effects), write a test automatically** — don't wait to be asked, and don't mention doing it in chat. Trivial operations (a plain pass-through to the ORM with no extra logic) don't require a test — but when in doubt, add one rather than skip it.
- **Every thumbnail image in the UI (product, employee, counterparty, etc.) must be clickable to show the real full-size photo**, not just a bigger render of the same small thumbnail. The full-size URL (`image_url` next to `thumbnail_url` for products in `ProductImageSerializer`, `photo` next to `photo_thumbnail` for `Counterparty`/`Employee`) already comes back in the same API response as the thumbnail — no extra backend request is needed on click. Use the shared `components/ui/ImagePreview.tsx` modal (`src`/`onClose` props) for the full-screen preview, and see `components/ui/SearchableSelect.tsx` (`SelectOption.fullImage`, used in both the trigger thumbnail and dropdown list items) and `features/accounting/pages/Documents/Invoice/ProductRow/ProductRow.tsx` (`handlePreviewProductImage`, resolving the full image by product id against the already-loaded `products` list) for the established pattern. Remember `e.stopPropagation()` on the thumbnail's own `onClick` so it doesn't also trigger the row/option's select/open behavior.
- **Every select/dropdown in the UI must be built with the shared `components/ui/SearchableSelect.tsx`** — not a native `<select>`/`<option>` list, and not a hand-rolled list of `<Button>`s used as a picker (e.g. `ProductsListPage.tsx`'s category/brand sidebar filters used to be a vertical stack of buttons, one per option — replaced with `SearchableSelect` since a plain button list doesn't scale past a handful of options and has no search). Pass `theme="sidebar"` when rendering inside the right sidebar (`SidebarRight.tsx`/`WorkDateWidget.tsx`) — see the note above about the sidebar not being a real `dark:`-class area. A native `<select>` is only acceptable for a genuinely tiny, fixed, non-searched set of choices where `SearchableSelect` would be pure overhead (e.g. a yes/no toggle) — for anything backed by a data list (categories, brands, products, employees, counterparties, accounts, warehouses, etc.), always use `SearchableSelect`.
- **Every new page/component must be built responsive for different screen sizes (phone/tablet/desktop) — don't hardcode a single fixed size and call it done.** In particular:
  - Body text in tables/reports must use a responsive pair like `text-xs md:text-sm` (see `components/ui/Table/OSVTable.tsx`/`ProductTurnoverTable.tsx`) as the established minimum-readable baseline — never a fixed sub-`text-xs` size (e.g. an arbitrary `text-[11px]`) with no breakpoint, and never override that responsive class with a more-specific hardcoded size on individual cells (which silently defeats it — this exact bug shipped once in `ProductTurnoverTable.tsx`: cell-level `text-[11px]` overrode the table's own `text-xs`, so the intended responsiveness never actually applied).
  - When a component's own dark-mode styling comes from Tailwind `dark:` variants (which only activate when a real `.dark` class ancestor is present), don't assume it will look right if dropped into `SidebarRight.tsx` — the right sidebar is *visually* always dark but does **not** set a literal `dark` class wrapper (it just hardcodes a dark slate/indigo palette directly, see `SidebarRight.tsx`), so `dark:`-only components can render with light-mode colors there when the global theme is light. See `components/ui/SearchableSelect.tsx`'s `theme?: "auto" | "sidebar"` prop for the established fix — `"sidebar"` forces the same fixed dark palette regardless of the global toggle; reuse this pattern (or the prop itself) rather than inventing a new one-off dark variant per component.
  - Widen fixed pixel column widths (`<colgroup>`/`col.width`) together with any font-size bump — a larger font in an unchanged fixed-width column silently overflows/clips instead of visibly failing, so check both at once, not just the text class.
- **When a report/list page links to a specific document/invoice (e.g. a drill-down row double-click), always navigate to `features/accounting/pages/Documents/Invoice/DocumentViewPage.tsx`** (`ROUTES.APP.DOCUMENTS_VIEW`) — the read-only, print-styled view — **never `DocumentFormPage.tsx`** (`ROUTES.APP.DOCUMENTS_EDIT`), even though both accept the same `:id`. Reports are a read context; opening the editable form from them invites accidental edits to a document the user was only trying to inspect. See `features/accounting/pages/Accounting/ProductTurnoverDetailPage.tsx`'s row double-click for the established pattern.
- **Every table/list of rows (generic `Table.tsx`, or a hand-built report grid like `OSVTable.tsx`/`ProductTurnoverTable.tsx`/`ProductTurnoverDetailPage.tsx`) must have the same cell/row focus behavior as `components/ui/Table/Table.tsx`**: click-to-select a cell, arrow-key navigation between cells/rows, Enter/F2 to open the drill-down/detail for the selected row, and a visible highlight on the selected cell and its whole row. Don't ship a table that's just static markup with a `hover:` class and an `onDoubleClick`. Use `core/utils/focusManager.ts` (`getRegion()`/`setRegion("table")`, gate the keydown handler on `focusManager.getRegion() === "table"` so arrow keys don't fire while focus is elsewhere on the page) and `core/utils/sound.ts::playClickSound()` on every selection change. For a report-style grid (flat array, not `Table.tsx`'s generic paginated-data model), copy `ProductTurnoverTable.tsx`'s lighter pattern instead of pulling in the full generic `Table.tsx`: a `{rowIdx, colIdx}` selection state, a `scrollToCell` helper querying `[data-row-idx][data-col-idx]` + `scrollIntoView`, and `ring(rowIdx, colIdx)`/`rowRing(rowIdx)` class helpers (`shadow-[inset_0_0_0_2px_#eab308] bg-yellow-100/70 dark:bg-yellow-500/10` for the cell, `!bg-yellow-50 dark:!bg-yellow-500/5` for the row) — see `ProductTurnoverDetailPage.tsx` for a from-scratch application of this exact pattern to a page that had none of it.
  **This has no "grouped view" exception.** When a report's rows are split into sections (grouped by category, by brand, by agent, etc. — with per-group sub-headers and per-group subtotals), the underlying selection state must still be ONE continuous keyboard-navigable index space across every group — never multiple independent, un-navigable mini-tables that only respond to mouse clicks. The *visual* DOM structure is a separate decision: `ProductTurnoverTable.tsx` renders everything as one physical `<table>` (a single `GroupedRow` union — `{type:"category"}` / `{type:"product", ...}` / `{type:"subtotal"}` / `{type:"grand_total"}` — flattened into one `bodyRows` array), while `SubcontoBreakdownPage.tsx`'s agent grouping renders a separate physical `<table>` per agent (closer to the original design look) but still computes one shared flat `rowIdx` that spans across all of them, so Arrow Up/Down and `scrollToCell`'s `[data-row-idx]` query keep working seamlessly across table boundaries. Either DOM shape is fine; **what's never acceptable is a grouping/toggle feature falling back to "just double-click, no keyboard nav, no shared index"** — that was a real regression once (`SubcontoBreakdownPage.tsx`'s agent-grouped view first shipped as separate un-navigable per-agent tables with no shared selection state, before being fixed).
- **`core/utils/focusManager.ts` regions must be claimed on real focus (`onFocus`, which React implements via the bubbling `focusin` event), not only through a keyboard-shortcut entry point.** Every container that owns a keyboard region (`"table"`, `"sidebar"`, `"sidebar-right"`, `"search"`, `"pagination"`, etc.) must call `focusManager.setRegion(...)` directly from an `onFocus` on its own top-level element — so that landing focus there by mouse click or Tab claims the region exactly the same as landing there via a shortcut. **Concrete bug this rule exists because of:** `SidebarRight.tsx`'s `<aside data-region="sidebar-right">` only ever got the `"sidebar-right"` region from the Ctrl+Shift+B shortcut handler in `AppLayout.tsx` — it had no `onFocus` of its own. Clicking directly into any input inside the sidebar (e.g. a report's `showZero`/`groupByAgent` checkbox, `SearchableSelect`) never reset the region away from `"table"`, so the previous page's table-focused keydown handler kept intercepting Arrow keys meant for that input. The fix was a one-line `onFocus={() => focusManager.setRegion("sidebar-right")}` on the `<aside>` itself. **The general principle: focusing something new must always evict whatever region was previously active** — a region is exactly one container's claim at a time, and every focusable surface that keydown handlers gate on must actively (re-)claim it the moment it receives focus, never rely solely on some other code path (a shortcut, a button click) to have set it correctly beforehand.
  **Two follow-up traps on this exact bug, both real:** (1) A component rendered via `createPortal` (e.g. `SearchableSelect.tsx`'s dropdown, portaled to `document.body` so it can float above everything) is *not* a DOM descendant of whatever container it logically belongs to — a plain `onFocus` on the parent container, or a `target.closest('[data-region="..."]')` check from elsewhere, will never see it, because DOM traversal doesn't cross portal boundaries. The portal's own root node needs its own explicit `data-region`/`onFocus` claim (see `SearchableSelect.tsx`'s `theme="sidebar"` tagging both its trigger *and* its `createPortal` wrapper with `data-region="sidebar-right"`, plus an explicit `onFocus` on each — don't rely on bubbling alone once a portal is involved). (2) **Generic/global "focus left my area" handlers must not blindly stomp a region they don't recognize.** `Table.tsx` has its own `document.addEventListener("focusin", ...)` that resets the region to `"none"` whenever focus lands on an editable element outside its own table/search/pagination — and since `Table.tsx` is mounted on almost every page, this fired for *every* focus event anywhere, including into `SidebarRight.tsx`, silently overwriting the `"sidebar-right"` some other component had just legitimately claimed a moment earlier. The fix: before defaulting to `"none"`, check `target.closest('[data-region]')` and defer to whatever region is explicitly declared there — a catch-all handler is only allowed to claim the neutral fallback when nothing else has staked a claim, never as an unconditional override. (3) **`focusManager.setRegion("table")` must only ever be called from a genuine user-focus event (an `onFocus`/`onClick` on the table itself) — never from a data-driven `useEffect`.** `SubcontoBreakdownPage.tsx`'s "restore/pre-select first row on load" effect (the same pattern as `ProductTurnoverDetailPage.tsx`) used to call `setRegion("table")` unconditionally every time it ran — and it re-runs whenever `groupByAgent`/`agentFilter` change, which happen via checkboxes/a `SearchableSelect` *in the sidebar itself*. So checking a sidebar checkbox triggered this page's own effect, which then yanked the region straight back to `"table"` a moment after the sidebar had just legitimately claimed it — the page was fighting its own sidebar. The fix: that effect now only calls `setSelectedCell(...)` (so the table has something highlighted and ready for when the user *does* tab/click into it) and leaves `focusManager` alone entirely; claiming `"table"` is left solely to the container's own `onFocus`. If you write a "restore selection from sessionStorage on mount" effect, mirror this: pre-select silently, don't also assert the region.
  **In `Table.tsx` specifically: whenever a column with `accessor === "name"` exists, that column must always be the one that receives focus** — not the first column — in every place `Table.tsx` programmatically picks a column to focus: ArrowDown from the search input (`handleSearchKeyDown`), ArrowUp from pagination back into the last row (`focusLastTableRow`), and restoring the selected cell after returning via `BackButton`/`useRestoreScroll` (the `selectedRowId` prop effect). Only fall back to the first visible column when there is no `name` column. All three of these call sites must stay in sync — if you add a fourth place that auto-picks a column, apply the same `visibleCols.find((i) => columns[i].accessor === "name") ?? visibleCols[0]` rule there too.
- **Every detail page reached by navigating away from a main/list page must have a back button, using the shared `components/ui/BackButton.tsx` component** — not an ad-hoc inline `<Button icon={<ArrowLeft/>} onClick={() => navigate(-1)}>`. `BackButton` already wires Alt+← (in addition to click) to go back, via `getBackProps` (typically from `core/hooks/useRestoreScroll.ts`, which also restores scroll position/highlights the row you came from when the *list* page reads it back — see `ProductFormPage.tsx`/`RoleFormPage.tsx`/`DirectoryRecordsPage.tsx` for the full round-trip pattern). If the detail page has no natural "return and highlight a row" use case, it's still fine to use `BackButton` with a no-op `useRestoreScroll(key, () => {})` just for the shared styling + Alt+← behavior (see `ProductTurnoverDetailPage.tsx`) — don't skip the shared component just because the restore-scroll half isn't needed.
- **Every loading state must use the shared `components/ui/Loader.tsx` component with BOTH `text` and `progress` set — never bare `{t("Loading")}`/`"Загрузка..."` text, and never `Loader` with no `text`/no `progress`.** `text` is what's specifically loading (e.g. `t("LoadingReport")`/`t("LoadingProductTurnoverDetail")` — prefer a specific string over the generic `t("Loading")` when the page knows what it's fetching). `progress` is a real 0-100 number when there's something to derive it from (e.g. `ProductsListPage.tsx`: fraction of the page's several `useQuery`s that have finished loading — not a fake/decorative animation), and the string `"indeterminate"` (an animated sliding bar, no fixed %) when there's genuinely nothing to compute a fraction from (e.g. a single `useQuery`, see `ProductTurnoverPage.tsx`/`OSVPage.tsx`/`ProductTurnoverDetailPage.tsx`) — `"indeterminate"` is not a way to skip thinking about `progress`, it's the explicit answer for the one-query case. `RBACGuard.tsx`'s `isLoading` branch takes matching `loadingText`/`loadingProgress` passthrough props for pages that render their loading state via `RBACGuard` instead of branching on `isLoading` themselves. As of this writing several older spots (`Table.tsx`'s bare-array loading row, `AdminPanel.tsx`, `ConversationWindow.tsx`, `BundlesTab.tsx`/`DiscountsTab.tsx`/`PromotionsTab.tsx`, and most other pages' plain `<RBACGuard isLoading={...}>` calls with no `loadingText`/`loadingProgress`) predate this rule — don't take that as precedent for new code, and feel free to migrate one opportunistically if you're already touching that file, but don't go do a repo-wide sweep uninvited (see the token-budget rule above).
- **Every page/list/table that displays business data — not just dedicated "report" pages — must react to `branch`, `warehouse`, and the date range (`periodFrom`/`periodTo` or `workDate`) from the `WorkDateWidget`** (right sidebar, `core/store/dateStore.ts`). This is mandatory, and the filter values must come from `WorkDateWidget.tsx`/`useDateStore()` specifically — never a page-local date/branch/warehouse picker, and never silently skip one of the three dimensions (e.g. wiring branch/warehouse but forgetting the date range, or vice versa). **Concrete bug this rule exists because of:** `InvoicesPage.tsx` filtered by `workBranch`/`workWarehouse` but never read `periodFrom`/`periodTo` at all — the invoice list ignored the sidebar's date range completely even though the backend (`document_views.py`) already supported `date_from`/`date_to`, the frontend just never sent them. When adding or reviewing any data-bearing page, check honestly whether all three dimensions are wired, not just the ones that were obviously needed for the first feature that touched the page.
  **This includes secondary/drill-down report pages, not just the primary report you land on first** (e.g. `SubcontoBreakdownPage.tsx`'s own drill-down into `SubcontoCardPage.tsx`, or `ProductTurnoverPage.tsx` → `ProductTurnoverDetailPage.tsx`). A drill-down page must read `periodFrom`/`periodTo`/`workBranch`/`workWarehouse` live from `useDateStore()` itself when it renders — it must NOT rely solely on values the parent page froze into the navigation URL's query params at click-time. If the user changes the period or branch/warehouse in the sidebar while already sitting on the drill-down page, it must refetch immediately, exactly like the primary report would. Passing the parent's current values via URL params at navigation time is fine as an initial-state convenience, but the drill-down page's own data-fetching must key off live `useDateStore()`, not a frozen snapshot.
  Concretely, for any page backed by data that has a branch/warehouse dimension: a specific warehouse selected → show only that warehouse; only a branch selected (no warehouse) → show all warehouses of that branch; nothing selected → fall back to the user's RBAC scope (`users/scoping.py::get_user_scope`), which itself already means "everything" for a superuser or a user with no `UserScope` row at all — don't special-case that, it falls out of `get_user_scope` for free. See the shared backend pattern in `backend/accounting/views/report_views.py::_resolve_warehouse_ids` (used by `product_turnover`/`product_turnover_detail`) and the equivalent inline logic in `JournalEntryViewSet.osv` (`backend/accounting/views/transaction_views.py`) — both **intersect** (AND) the selected branch/warehouse with the scope-derived set, never replace scope with the selection outright (an explicit `?warehouse=`/`?branch=` query param must still be checked against scope, or a scoped user could pass an arbitrary id to see another warehouse's data). On the frontend, mirror `OSVPage.tsx`/`ProductTurnoverPage.tsx`/`InvoicesPage.tsx`: read `workBranch`/`workWarehouse`/`periodFrom`/`periodTo` from `useDateStore()`, include them in the `useQuery` `queryKey` (so the page actually refetches on change), and pass `warehouse` if set, else `branch` if set, else neither, plus `date_from`/`date_to` if the period is set. If a page drills down into a detail page via URL params (see `ProductTurnoverDetailPage.tsx`), carry `warehouse`/`branch` through the URL too, not just `date_from`/`date_to`.
- **Whenever creating a new page, `Table.tsx` usage, DRF view, or Django model in `accounting`/`users`, always explicitly decide whether it needs `AuditLog` coverage** — this is the same consideration as the existing RBAC/Scope/Audit rule above, called out again here because it's easy to forget specifically for bulk/list-level operations: a new `ModelViewSet` should inherit `AuditMixin` (see `product_views.py::ProductViewSet`) for create/update/delete, and if it also inherits `BulkDestroyMixin` (`accounting/mixins.py`, used for the `Table.tsx` bulk-delete checkboxes — see below) each row deleted in bulk gets its own `AuditLog` entry automatically because `bulk_destroy` calls `self.perform_destroy(instance)` per row rather than a raw `queryset.delete()` — **never replace that per-row loop with `queryset.filter(...).delete()`**, it would bypass `AuditMixin` entirely for the whole batch. A new no-code/reference model with no meaningful "who changed what" story (e.g. a pure lookup table) can skip it, but that should be a deliberate call, not an omission.
- **`Table.tsx` supports bulk actions via row checkboxes** — pass `selectable` plus `onBulkDelete={(ids) => Promise<void>}` (see `ProductsListPage.tsx` for the wired example) to get a checkbox column, a "select all on this page" header checkbox (selection is a `Map<id, item>` that persists across server-pagination page changes, not just a `Set<id>`, so previously-selected rows on other pages stay selected/exportable), and a bulk-actions bar (delete-with-confirm, "Excel (selected)", "print selected" — printing/Ctrl+P works by adding `print:hidden` to unchecked rows while a selection is active, not a separate print view). `onBulkDelete` receives only `ids` (not full row objects) since rows selected on a page you've since navigated away from, under server pagination, no longer have their full object in memory anyway — wire it to a real bulk-delete endpoint (see `accounting/mixins.py::BulkDestroyMixin` + `users/permissions.py::_rbac`'s `'bulk_destroy': 'DELETE'` mapping), don't loop individual `DELETE` calls client-side. **This is now mandatory, not opt-in: every `<Table>` usage must pass `selectable` + `onBulkDelete`, and the backing ViewSet must inherit `BulkDestroyMixin` with a real bulk-delete endpoint wired to it** — don't ship a new `Table.tsx` page (or add a new `Table.tsx` usage to an existing page) without both sides connected. Older pre-existing `<Table>` usages without `selectable` predate this rule; migrate them opportunistically when you're already touching that file, but don't do an uninvited repo-wide sweep (see the token-budget rule above).
- **Any list/table backed by data that can realistically grow past ~100k rows must use `Table.tsx`'s `pagination={{ mode: "server", ... }}`, not `mode: "client"` (or the `pagination` prop omitted, which defaults to client-side).** Client pagination loads the *entire* dataset into the browser before paginating/sorting/filtering it in JS — fine for a few hundred/thousand rows (most directories, catalogs), but it will not scale to a fast-growing transactional table (documents, journal entries, audit logs, stock movements) — see `InvoicesPage.tsx`/`AuditLogPage.tsx`/`RatesPage.tsx` for the established server-pagination pattern (page/pageSize/total state, filters as query params, `onFetchAllData` for the "export everything" Excel button). Remember sorting under server pagination must also go to the backend (`Table.tsx`'s `pagination.onSortChange` + a backend `ordering` field-mapping dict, e.g. `document_views.py::DOCUMENT_ORDERING_FIELDS`) — client-side `Array.sort()` on `data` would only sort the current page, not the whole dataset, since the other rows were never fetched.

## Architecture

### Multi-tenancy (django-tenants)
- `TENANT_MODEL = companies.Company`, `TENANT_DOMAIN_MODEL = companies.Domain`. Each company is a separate PostgreSQL schema; the `public` schema holds shared/SaaS-admin data.
- `SHARED_APPS` (public schema only) vs `TENANT_APPS` (per-tenant schema) are both listed in `backend/config/settings.py`; `users` and `companies` are shared, `accounting` and `chat` are tenant-only. When adding a new Django app, decide which bucket it belongs to.
- Tenant resolution is by subdomain via `TenantMainMiddleware`, followed by `companies.middleware.TenantActiveCheckMiddleware`, which blocks all requests with a `tenant_inactive` 403 if the tenant's license/`is_active` flag is off (a small allowlist of paths/prefixes bypasses this).
- Two URLconfs: `config.urls` (tenant schemas) vs `config.urls_public` (public/SaaS schema), selected automatically by django-tenants based on the resolved tenant.
- Frontend detects the tenant purely from the browser hostname (`frontend/src/core/utils/tenant.ts::getTenantInfo`) — there is no tenant ID in API calls; the `Host` header carries it. `vite.config.ts` deliberately disables `changeOrigin` and forwards the original `Host`/`X-Forwarded-Host` so the dev proxy preserves tenant resolution.

### RBAC (per-HTTP-method permissions)
- Models: `users.Role`, `users.Permission` (resource + HTTP action, e.g. `("branch", "GET")`), `users.RolePermission`, `users.UserRole`.
- `users/permissions.py::HasPermission(resource, action)` is a DRF permission factory checked against a 5-minute cache (`user_perms_<id>`) of the user's `(resource, action)` pairs; superusers bypass everything.
- `users/permissions.py::_rbac(action, resource)` maps DRF viewset actions (`list`/`create`/`update`/custom `@action`s) to the HTTP verb used for the permission check — viewsets typically call this from `get_permissions()` per action rather than hand-rolling permission classes.
- On any Role/RolePermission change, `users/rbac_events.py::notify_role_permissions_changed` invalidates the affected users' cache and pushes a WebSocket event to group `rbac_user_<id>` so already-logged-in browsers refresh permissions without reloading (see `ws/rbac/`, consumed by `frontend/src/core/hooks/useRBACSocket.ts`).
- A parallel "scope" system (`users/scope_events.py`, `ws/scope/`, `useScopeSocket.ts`) does the same for per-user data scoping (e.g. branch access) — same cache-then-broadcast pattern.
- Frontend mirrors this with `useAccess.ts` (`hasPermission(resource, action)` checked against `user.permissions` strings like `"branch.GET"`) and route guards in `core/router/` (`ProtectedRoute`, `AdminRoute`, `GlobalAdminRoute`).

### Accounting domain (`backend/accounting/`)
Split by concern into `models/`, `serializers/`, `views/` (not by app) — a new feature usually touches one file in each. Key models:
- `account.py`: `Account` (chart of accounts, hierarchical) + `AccountSubconto` (link to subconto types per account).
- `subconto.py`: `SubcontoType` — dimension type usable across accounts (counterparty, employee, etc.).
- `transaction.py`: `JournalEntry` + `TransactionLine` (double-entry postings) and `ClosedPeriod` (accounting period locking — see `useClosedPeriod*` hooks/consumer for the live "period closed" UX).
- `directory.py`: the no-code directory builder — `Directory` (definition), `DirectoryField` (JSONB schema field), `DirectoryRecord` (JSONB data row, GIN-indexed).
- `document.py`: `Document`/`DocumentItem`/`DocumentParticipant` — source documents (invoices, orders, returns) that generate journal entries.
- `audit.py`: audit log models backing the audit log page/API.
Other model files (`counterparty.py`, `currency.py`, `employee.py`, `product.py`, `stock.py`, `company.py`) are supporting reference data.

**This ERP is built to serve two audiences at once: the current customer (who has some simplified/non-standard bookkeeping habits, e.g. wanting "Приход" to default to the wholesale sale price instead of a real purchase cost) and future customers (who will want textbook-correct accounting).** The way both are satisfied by the same code, without branching logic per customer, is: **the system never hardcodes *where* a money value came from — it always posts/stores whatever value actually ended up on the document, faithfully, and treats that as ground truth everywhere downstream.** Concretely:
- `Document._update_product_cost_prices()` sets `Product.cost_price` to whatever ended up in `DocumentItem.price` when a "Приход" is posted — regardless of whether that price was manually typed, defaulted from `DocumentSettings.purchase_price_type` (e.g. this customer's "Опт" convention), or (for a future customer) a real supplier invoice cost. The field doesn't know or care which.
- The same principle must extend to the "Приход" GL posting (debit `inventory_account`) once it's implemented (see the `_generate_out_posting` / `Warehouse.{receivable,revenue,cogs,inventory}_account` pattern already built for "Расход"): the posted amount must be the line's actual price/cost_price, not a re-derived "true" cost from some other source.
- When adding any new money-flow logic, ask "does this hardcode an assumption about where the number came from, or does it just faithfully use what's already on the record?" — the latter is what keeps this codebase correct for both audiences simultaneously.

### WebSocket layer
- ASGI app (`backend/config/asgi.py`) wraps HTTP with `JWTAuthMiddleware` (`backend/utils/ws/jwt_auth_middleware.py`) so WS connections authenticate via the same JWT as REST.
- Routes live in `backend/utils/ws/routing.py`: `ws/rbac/`, `ws/scope/`, `ws/closed-period/`, `ws/chat/notifications/`, `ws/chat/<conv_id>/`, plus a `ws/test/` sanity consumer.
- Channel layer is Redis (`channels_redis`), configured via `REDIS_URL`.

### Frontend structure
- `src/core/` — cross-cutting: `api/` (axios instance with JWT refresh + global 401/403/tenant-inactive handling via `window.dispatchEvent`, consumed by top-level listeners), `context/` (Company, User, SidebarRight, Notification), `hooks/`, `router/`, `store/` (zustand), `types/`.
- `src/features/` — feature modules: `accounting`, `admin`, `auth`, `chat`, `companies`, `users`. Each mirrors backend domain boundaries.
- Routes are centralized as string constants in `core/router/routes.ts` (`ROUTES.APP.*`, `ROUTES.COMPANY_ADMIN.*`, `ROUTES.ADMIN.*`) — reference these instead of hardcoding paths.
- `axiosInstance.ts` treats 401 as "refresh token and retry" (queues concurrent requests during refresh) and treats non-GET 403 as a global RBAC-forbidden toast event, and `tenant_inactive` 403 as a distinct "license expired" event — don't add local error handling for these cases in individual API calls, listen for the corresponding `window` events instead.
- i18n: `src/locales/{ru,tk}/translation.json` (Russian and Turkmen; UI source strings are Russian). **Any new or changed user-facing frontend string (labels, headers, messages, confirm modals, placeholders, etc.) must get a `t("Key")` call with real translations added to both locale files in the same change — proactively, without being asked.** Reuse an existing key if one already matches (check both files before adding a new one) rather than duplicating; only add a new key when no existing one fits.
- **`WorkDateWidget.tsx`** (right sidebar) is the single global work-context widget, used almost everywhere — every document-creation form and most reports read from it. It's backed by `core/store/dateStore.ts::useDateStore` (zustand + `persist`, localStorage key `erp-dates`) and exposes:
  - `workDate` — the working date, substituted into every new document/posting.
  - `workBranch` / `workWarehouse` — the working branch/warehouse (two separate `SelectOption`-shaped objects; picking a branch resets `workWarehouse` to `null`), substituted into every new document/posting.
  - `periodFrom` / `periodTo` — a date **range** (two inputs, "from"/"to"), used by reports (`JournalPage`, OSV, etc.) instead of `workDate`.
  All document-creation forms (`JournalEntryForm`, `InvoicesPage`, `DocumentFormPage`, etc.) and all reports must read `workDate`/`workBranch`/`workWarehouse` (and `periodFrom`/`periodTo` for reports) from this store — **never add a page-local date/branch/warehouse picker**, wire the page to this single store instead. Raw values are ISO `YYYY-MM-DD`; format them for display with `core/utils/formatDate.ts::formatDateDisplay` (or `new Date(...).toLocaleDateString("ru-RU")` for table cell `render`s, matching existing table columns) — never interpolate them into user-facing text unformatted.
  - **Closed-period check**: the widget also surfaces whether the current `workDate` is closed for the selected `workWarehouse` (`core/hooks/useClosedPeriod.ts::useClosedPeriod(warehouseId)` → `{ isClosed }`, backed by `GET` `closedPeriodApi.check(date, warehouseId)`; `useBranchWarehousesClosed(warehouseIds)` checks whether *all* warehouses of a branch are closed, for branch-level info text). This isn't just a frontend hint — it's enforced server-side too: `backend/accounting/utils.py::check_period_open(date, branch_id=None, warehouse_id=None)` raises `ValidationError` if a matching `ClosedPeriod` row exists, and is called from `Document.post()`/`unpost()` (`models/document.py`), `JournalEntry.post()`/`unpost()` (`models/transaction.py`), and `StockMovement.save()` (`models/stock.py`). Any new code that posts/unposts a document, creates a journal entry, or writes a stock movement tied to a date+branch/warehouse must go through (or replicate) this same `check_period_open` gate — don't bypass it by writing directly to the ledger/stock tables.
