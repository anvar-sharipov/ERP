Краткая памятка: как обновить сервер, если поменялся только код
(backend и/или frontend), без изменений в docker-compose.yml/nginx.conf/.env
и без новых данных (дамп/media не нужны).


Шаг 1. На dev-машине (там, где интернет), из корня репозитория:

docker compose build backend nginx


Шаг 2. Сохранить оба образа в .tar (из папки пакета):

docker save -o backend-erp.tar my_erp-backend:latest
docker save -o nginx-erp.tar my_erp-nginx:latest


Шаг 3. Перенести на сервер только эти два файла (остальное — postgres/redis/
dns/openssl образы, дамп, media — не нужны, они не менялись).


Шаг 4. На сервере — загрузить образы:

docker load -i backend-erp.tar
docker load -i nginx-erp.tar
docker images   (проверить, что дата создания образов — свежая)


Шаг 5. На сервере — запустить:

.\start.ps1
Если выдаст ошибку про "выполнение скриптов отключено" (execution policy), тогда один раз разрешить (от администратора):
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
и повторить .\start.ps1.

(НЕ голый "docker compose up -d" — start.ps1 заодно обновляет hardware_id.txt,
см. instruction.txt про привязку к ПК)


Что происходит само, не забывать пугаться:
- Миграции применяются автоматически — команда старта backend уже включает
  "migrate_schemas --shared && migrate_schemas", отдельно накатывать не нужно.
- celery-worker и celery-beat тоже пересоздадутся вместе с backend — они
  используют тот же образ my_erp-backend:latest, это нормально, не отдельный шаг.
- Если docker-compose.yml/nginx.conf/.env не менялись — их на сервере
  перекопировать не нужно, только два .tar.
- DNS/hosts/файрвол трогать не нужно — не зависят от образов кода.

Доступ с клиентских ПК (hosts-файл — обязательно на КАЖДОМ ПК):

Настройка DNS-сервера на сетевом адаптере (указать IP сервера как DNS)
оказалась ненадёжной — штатный DNS-клиент Windows (которым пользуются
браузер/curl) падает с ошибкой на запросах к dnsmasq-контейнеру сервера,
хотя nslookup при этом резолвит нормально. Поэтому на каждом ПК, с которого
будут заходить в программу, нужно один раз (от администратора) прописать
запись в hosts:

Add-Content -Path C:\Windows\System32\drivers\etc\hosts -Value "192.168.43.245 polisem.erp.local"

Если IP сервера снова поменяется — эту строку нужно поправить (заменить IP)
на КАЖДОМ таком ПК, не только на сервере (это неудобство hosts-подхода —
он не централизован). Если ПК много и IP меняется часто, стоит отдельно
разобраться, почему DNS-клиент Windows конфликтует с dnsmasq, и наладить
DNS-путь по-нормальному вместо hosts на каждой машине.

Смена сети/IP сервера (например, перенесли на другую сеть 192.168.100.0/24,
дали IP 192.168.100.10) — минимум шагов, ради этого и перешли на erp.local:

На сервере:
1. Поправить dnsmasq.conf: address=/erp.local/192.168.100.10 (новый IP)
2. docker compose restart dns

На КАЖДОМ клиентском ПК:
3. Поправить IP в hosts-файле (убрать старую строку, добавить новую):
   192.168.100.10 polisem.erp.local

Трогать НЕ нужно:
- nginx.conf — там server_name erp.local *.erp.local;, IP не упоминается.
- docker-compose.yml / образы — не зависят от IP.
- Правила файрвола (8100/8101/53) — привязаны к портам, не к IP/сети.
- База данных / companies_domain — домены зарегистрированы как
  polisem.erp.local, а не как IP, их тоже не нужно трогать. Это и есть
  главный смысл erp.local вместо "имя+IP" — при смене сети/IP правится
  только dnsmasq.conf + hosts на клиентах, ничего больше.

Вне зоны этих файлов — сама физическая связность (новая сеть должна быть
реально доступна с клиентских ПК, это вопрос инфраструктуры/роутера).

Резервные копии и восстановление 
(backup.ps1 / restore.ps1)

Автоматические бэкапы — уже настроены на сервере:
- Планировщик Windows, задачи "ERP Backup 12-00" и "ERP Backup 18-00" —
  ежедневно в 12:00 и 18:00 запускают C:\ERP\backup.ps1.
- backup.ps1: дамп БД (pg_dump -Fc, пишется ВНУТРИ контейнера erp-db-1,
  выносится через docker cp — не через пайп PowerShell, иначе бинарный
  формат/кириллица может побиться) + архив media (tar внутри контейнера,
  монтирующего том erp_django_media) → C:\erp_backups\<дата_время>\ +
  копия на D:\erp_backups\<дата_время>\ (второй физический диск).
- Ротация: бэкапы старше 30 дней удаляются автоматически (и на C:, и на D:) —
  иначе за годы работы это ~1 ГБ/день съест весь диск.
- ВАЖНО: задачи зарегистрированы с типом входа "Interactive" — сработают,
  только если пользователь (учётка, под которой это настроено) реально
  залогинен в Windows на сервере в этот момент (простая БЛОКИРОВКА экрана,
  Win+L, — это НЕ разлогинивание, задача всё равно сработает). Если сервер
  часто остаётся на экране входа без активной сессии — нужно перерегистрировать
  задачи с паролем учётки (Run whether user is logged on or not).
- Ручной запуск в любой момент: cd C:\ERP; .\backup.ps1

Восстановление (СЕРВЕР) — C:\ERP\restore.ps1:
  .\restore.ps1                              — покажет список папок в
                                                C:\erp_backups, спросит какую
  .\restore.ps1 -BackupName 2026-07-31_18-00 — конкретный бэкап
Подтверждение — ввести ТОЧНО слово "ВОССТАНОВИТЬ" (не "да"/"yes"/Enter).
Что происходит: 1) сам делает safety-бэкап текущего состояния (переименовывает
в "<дата>_pre_restore_safety" — можно откатиться назад, если выбрали не тот
бэкап), 2) останавливает backend/celery-worker/celery-beat, 3) pg_restore
--clean --if-exists из выбранной папки, 4) распаковывает media (полностью
заменяет содержимое тома), 5) поднимает всё обратно (docker compose up -d).
Сознательно НЕ кнопка в веб-админке — backend-контейнер не должен иметь
доступ к Docker-сокету хоста (дыра в безопасности), и restore ломает
работающий бэкенд прямо во время своего выполнения.

Бэкап/восстановление на DEV-МАШИНЕ (не сервер, нативный Postgres на Windows,
НЕ Docker — см. CLAUDE.md) — tools\backup_dev.ps1 / tools\restore_dev.ps1 в
репозитории. Тот же формат вывода (erp_db.dump + media.tar.gz в датированной
папке C:\erp_backups\<дата>\), что и на сервере — папку можно просто
скопировать на сервер и восстановить штатным restore.ps1 там.

Типичный сценарий "перенёс/проверил данные на dev — залил на сервер":
  1. На dev-машине: .\tools\backup_dev.ps1
  2. Скопировать полученную папку C:\erp_backups\<дата> на сервер, в
     C:\erp_backups\<дата> (та же дата/имя папки)
  3. На сервере: cd C:\ERP; .\restore.ps1 -BackupName <дата>

restore_dev.ps1 (на dev-машине) перед восстановлением (dump) требует остановить
всё, что держит соединение с БД (manage.py runserver/daphne) — активные
соединения могут помешать pg_restore --clean.
